# The job

What `wb plan add` takes in and how a job is kept in git: its text a blob under its hash, its name a ref. What was decided: [docs/revision.md](../docs/revision.md), point 15. `wb add` was folded into `wb plan add` on 2026-11-24 (#290).

| ID | Requirement | Ver | Status |
|---|---|---|---|
| WB-JOB-1 | `wb plan add -F -` shall store the text it reads from standard input as a git blob under the hash of that text, and end with 0. Issue: #234. | T | Implemented |
| WB-JOB-2 | `wb plan add` shall make the ref `refs/watchbill/<name>` point at a commit whose tree holds `job.yml` and the text of each source kept, under `sources/<hash>`. A name may hold `/`. Issue: #234. | T | Implemented |
| WB-JOB-3 | `job.yml` shall hold the name the job was first taken in under, all its names, and for each source in the order it was added, the hash of its text, whether the text is kept, the source (`--source <address>`, or `none`), the level, the person's git identity and the time. Issue: #234. | T | Implemented |
| WB-JOB-4 | `wb plan add -F <file>` and `wb plan add -m <text>` shall give the same hash as standard input does for the same text. A relative file is read from the folder `wb` runs in, and only where it is a plain file: a FIFO, a device or a folder shall end with 1, naming `-F -` for a pipe, without waiting on it. A text that is empty, not UTF-8 or over 1 MiB shall end with 1, and nothing shall be written. Issue: #234. | T | Implemented |
| WB-JOB-5 | `wb plan add` shall end with 2 and write nothing when it is given none of `-F`, `-m` and `--from`, or more than one of them, or `-F` or `--from` twice. Issue: #234. | T | Implemented |
| WB-JOB-6 | With no name, `wb plan add` shall name the ref with the first 12 hex digits of the hash of the text. Issue: #234. | T | Implemented |
| WB-JOB-7 | `wb plan add` given text that is already a source of the job of that name shall write no new commit and end with 0. Issue: #234. | T | Implemented |
| WB-JOB-8 | `wb plan add` given other text under a name already taken shall add it as a source: a new commit on the ref that names the commit before it, and whose tree keeps the sources there and holds the new one. Issue: #234, #290. | T | Implemented |
| WB-JOB-9 | `wb plan add` given other text under a name already taken shall say the hashes of the sources there and the hash of the one it adds. Issue: #234, #290. | T | Implemented |
| WB-JOB-10 | `wb plan add` shall end with 1, name the rule and write nothing when `git check-ref-format` refuses `refs/watchbill/<name>`, as for a name with `:`, or when the name meets the name of a job as a folder. Issue: #234. | T | Implemented |
| WB-JOB-11 | `wb plan add` shall end with 1 and write nothing when there is no organisation's file, or `--level <level>` is not one of its levels or is above the repository's. With no `--level`, the level is the repository's. Issue: #234. | T | Implemented |
| WB-JOB-12 | `wb plan add --hash-only` shall end with 1 and write nothing unless the organisation's file has `jobs: hash_only: allowed`. Issue: #234. | T | Implemented |
| WB-JOB-13 | `wb plan add --hash-only`, where the organisation's file allows it, shall write no blob of the text, and `job.yml` shall hold the hash of the text and its source. Issue: #234. | T | Implemented |
| WB-JOB-14 | `wb plan add` shall say what it will write (the blob, `job.yml`, the tree and the commit on the ref) before it writes it. Issue: #234. | T | Implemented |
| WB-JOB-15 | `wb plan add` with `-F` or `-m` shall ask nothing of the network and run no pattern. Issue: #234. | T | Implemented |
| WB-JOB-16 | `wb plan add` shall only queue the job: it shall run no prompt and start no session. Issue: #234. | T | Implemented |
| WB-JOB-17 | `wb init` shall add the fetch line `+refs/watchbill/*:refs/watchbill/*` to the remote `origin` in `.git/config`, where `origin` is there, and say so before it writes. Issue: #234. | T | Implemented |
| WB-JOB-18 | `wb upgrade` shall add the fetch line `+refs/watchbill/*:refs/watchbill/*` to the remote `origin` where it is missing, and say so before it writes; `--dry-run` shall say it and write nothing. Issue: #234. | T | Implemented |
| WB-JOB-19 | `wb upgrade` shall leave the fetch line as it is where it is already there. Issue: #234. | T | Implemented |
| WB-JOB-20 | `wb help plan` shall say what `wb plan add` takes in, how it names a job, its options and its exit statuses. Issue: #234. | T | Implemented |
| WB-JOB-21 | `wb plan add -m <text>`, given more than once, shall join the texts as `git commit -m` does: each on a line of its own after the one before, then cleaned up as `git stripspace` does (whitespace at the end of a line taken off, runs of blank lines made one, blank lines at the start and the end taken out). Issue: #234. | T | Implemented |
| WB-JOB-22 | `wb plan add` given, under a name that is not taken, text that is a source of a job already shall give that job the name: a new commit whose `job.yml` lists it, with the new ref and every ref that pointed at the job's commit moved to it in one transaction. A later source under any name of the job shall move every ref that points at the commit before, in one transaction with the values they had. Looking for the text, a ref under `refs/watchbill/` that is not a job shall be passed over and said once on standard error. Issue: #234. | T | Implemented |
| WB-JOB-23 | `wb plan add --from <adapter> <number>` shall end with 2, say to pipe the text in with `-F -`, and run nothing, where no adapter of that name is set up: until adapters are built, where `tracker:` of `watchbill.yml` is not the adapter or the file has no `issue_text`. Issue: #234. | T | Implemented |
| WB-JOB-24 | `wb plan add --from <adapter> <number>` shall take the text that `issue_text` prints for the number, as `-F -` takes it, name the job `<adapter>/<number>`, and keep the command it ran as the source. A number that is not digits, a name, or `--source` given with it shall end with 2. Issue: #234. | T | Implemented |
| WB-JOB-25 | The organisation's file may have `jobs: hash_only:` with `allowed` or `refused`, read through the one loader; any other key or value under `jobs` shall be refused, with the place named. Issue: #234. | T | Implemented |
| WB-JOB-26 | `wb plan` with no subcommand, or one that is not known, shall end with 2 and name `add, list, show, edit, accept, remove`. There shall be no command `wb add`. Issue: #234, #290. | T | Implemented |
| WB-JOB-27 | `wb plan list` shall print each plan once, by its first name, one to a line in the order of the names, and nothing else, and end with 0. Issue: #290. | T | Implemented |
| WB-JOB-28 | `wb plan list` shall leave out a plan removed, and pass over a ref under `refs/watchbill/` that is not a job, saying it once on standard error. Issue: #290. | T | Implemented |
| WB-JOB-29 | `wb plan show <name>` shall print the plan's names and each of its sources, in the order they were added, with its hash, where it came from, whether its text is kept, its level, who added it and when. Issue: #290. | T | Implemented |
| WB-JOB-30 | `wb plan show <name>` shall print the plan's issue's file, `.watchbill/issues/<name>.yml`, read with its `.accepted` where `wb status` reads them (the first branch of the name by the pattern `branch`, local before `origin`, else the working tree), after a line that says which it read and a line `state:` that is `not planned` where the file is not there, `not accepted`, or `accepted by <who> at <time>` from `.accepted`. Issue: #290. | T | Implemented |
| WB-JOB-31 | `wb plan show`, `edit` and `remove` of a name that is no plan, and `show`, `edit`, `accept` and `remove` of a plan removed, shall end with 1, name `wb plan list`, and write nothing. Issue: #290. | T | Implemented |
| WB-JOB-32 | `wb plan edit <name>` shall open the plan's issue's file in the editor git would use (`git var GIT_EDITOR`: `GIT_EDITOR`, `core.editor`, `VISUAL`, `EDITOR`), and commit the file alone, as the person, with the message `Edit the issue's file (<name>)`, leaving what else is staged out of the commit. Issue: #290. | T | Implemented |
| WB-JOB-33 | `wb plan edit <name>` shall commit nothing, say so, and end with 0 where the editor left the file as it was. Issue: #290. | T | Implemented |
| WB-JOB-34 | `wb plan edit <name>` shall end with 1 and open no editor where the checkout is not on the issue's branch or the file is not committed in `HEAD` as it is; and end with 1, commit nothing and leave the edit in the working tree where the editor ends with other than 0, the file no longer holds its form, or its `issue:` is not the plan's name. It shall say that an acceptance holds no longer only where one was there. Issue: #290. | T | Implemented |
| WB-JOB-35 | After `wb plan edit` changes an accepted file, `wb plan show` shall say `not accepted (edited after the acceptance)`. Issue: #290, #76. | T | Implemented |
| WB-JOB-36 | `wb plan accept <name> [--no-commit]` shall accept the plan's issue's file as `wb accept <issue>` did (WB-TASK-1 to WB-TASK-6, WB-TASK-8, WB-TASK-9, WB-TASK-19 to WB-TASK-30): the same checks, the same `.accepted`, the same commit alone, with its messages starting `wb plan accept:`. Where the default branch has `.watchbill/signers`, it also makes the signed tag of WB-TASK-31 and posts the `[accepted]` notice of WB-TASK-39 by `issue_comment`, beside what WB-TASK-30 allowed (#235). Issue: #290. | T | Implemented |
| WB-JOB-37 | `wb plan show` of a plan whose name is not an issue's name shall say that it has no issue's file, and `wb plan edit` and `wb plan accept` of it shall end with 1. Issue: #290. | T | Implemented |
| WB-JOB-38 | `wb plan remove <name>` shall add a commit after the plan's whose tree keeps what was there and adds `removed`, with the person's git identity and the time, move every name of the plan to it in one transaction, rewrite nothing, and say what it writes before it writes it. Issue: #290. | T | Implemented |
| WB-JOB-39 | `wb plan remove <name>` shall end with 1, write nothing and name what holds it while a branch of any name of the plan, by the pattern `branch`, holds a commit the default branch does not and is not done as `wb status` reads it, or this machine keeps a view of any name of it with work not taken back. Issue: #290. | T | Implemented |
| WB-JOB-40 | `wb plan add` under the name of a plan removed shall end with 1 and write nothing, and text that is a source of a plan removed shall not be taken as that plan's. Issue: #290. | T | Implemented |
| WB-JOB-41 | A source added to a plan in the same second as the `time:` of its `.accepted` or later shall void the acceptance: `wb plan show` says `not accepted (a source added after the acceptance)`, `wb status` puts the plan under `Planned`, and no prompt of a role of it is handed out. Issue: #290. | T | Implemented |
| WB-JOB-42 | A `[stamp] planner` whose `time:`, read by `issue_comment_bodies`, is the same as or later than the `time:` of the plan's `.accepted` shall void the acceptance, even where the file came out the same: `wb plan show` says `not accepted (planned again after the acceptance)`, `wb status` puts the plan under `Planned`, and `wb start` and `wb prompt` of a role of the issue end with 1, hand out no prompt and name `wb plan accept <name>`, reading the stamps as `wb status` does. A stamp that a `[revert]` took back counts for nothing. An acceptance written after it holds again. Issue: #290. | T | Implemented |
| WB-JOB-43 | `wb accept <name>` where the issue's file is not accepted, a plan of the name being there or not, or its acceptance is void by a source or a planner round after it, shall end with 2, write nothing and name `wb plan accept <name>`; `wb plan accept <name>` shall also accept an issue's file with no plan (#282). Issue: #290. | T | Implemented |
| WB-JOB-44 | `wb start planner <name>` of a plan shall bring every source of the plan, in the order they were added, into `.watchbill/issue/<name>.md` of the view, each under a line `--- source <n>: <hash>, from <source> ---` where there is more than one, and shall run no `issue_text`. Issue: #290. | T | Implemented |
| WB-JOB-45 | `wb help plan` shall say what `list`, `show`, `edit`, `accept` and `remove` do, their options and their exit statuses. Issue: #290. | T | Implemented |
